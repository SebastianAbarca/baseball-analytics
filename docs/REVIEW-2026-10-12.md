# Implementation and conceptual review — 12 October 2026

The product idea is coherent: describe players with evidence-bearing traits, combine them into roster profiles, and keep expensive analysis separate from serving. The implementation is not yet reliable enough to endorse its tags or team comparisons as analytically sound. Several problems reverse the meaning of a metric, mix incompatible samples, or allow stale data to appear current. Correctness and reproducibility should precede additional modeling or infrastructure.

This was a review, not a repair. Application code, data, and database contents were not changed. The pre-existing edits to TAGS.md and dashboard/tag_reference.json were preserved.

## Scope and evidence

Reviewed the ingestion, aggregation, normalization, trait, portrait, refresh, publishing, serving, similarity, schema, deployment, and validation paths directly. Compared these with README, ARCHITECTURE, DECISIONS, OPERATIONS, and the generated tag reference. Inspected the installed pybaseball season helpers rather than assuming their names imply regular-season totals.

Local checks covered all 360 saved portraits and all twelve season parquet files for game types and duplicate pitch keys. Deeper numerical checks used 2022, 2023, 2025, and 2026. Eight existing offline validation functions passed: V1–V6, V11, and V12. The tag-reference check also passed. Targeted synthetic and mocked tests reproduced direction, pairing, fingerprint, and publishing failures without external writes.

The local snapshot contains 19,057 player/team/season/side entries, 17,094 distinct player/season/side combinations, 94 tags, and 82,414 tag firings. These are local artifact counts, not verified production counts. All 360 portraits passed the current freshness predicate. No duplicate `(game_pk, at_bat_number, pitch_number)` keys were found in the twelve raw files.

Not performed: a fresh full rebuild, live database/schema verification, deployment testing, a load test, or execution of every notebook. Passing the selected existing checks does not validate the statistical claims below.

## Confirmed issues affecting results

### 1. High priority: contact suppression is ranked backward

[team_portrait.py:794](../baseball_construction/modules/team_portrait.py#L794) deliberately leaves hard-hit and barrel rates uninverted because its comments assume Savant supplied already-inverted percentiles. The ingestion repair now supplies **raw rates allowed** instead. [pitcher_traits.py:563](../baseball_construction/modules/pitcher_traits.py#L563) then labels high rates as `contact suppressor`.

Recomputing against the local historical pool gave Joe La Sorsa's 20.7% hard-hit rate a 0.62 percentile and Zach Pop's 66.7% a 99.97 percentile. Gordon Graceffo's 53.6% was ranked about 98.6; his saved 2025 portrait carries `contact suppressor`. This is an actual semantic reversal, not merely an unfortunate label. It propagates into cards, team densities, and similarity.

**Repair:** establish an explicit direction for each canonical raw metric, invert suppression once, and rebuild every downstream artifact. Add a monotonicity check: allowing less hard contact must never reduce the suppression score.

### 2. High priority: pull and opposite-field directions are reversed

[pitch_aggregates.py:463](../baseball_construction/modules/pitch_aggregates.py#L463) defines positive spray angles as right field, then calls right field the pull side for a right-handed hitter. The corresponding team spray logic repeats this in [team_portrait.py:3530](../baseball_construction/modules/team_portrait.py#L3530).

A synthetic right-handed batter hitting exclusively toward the code's right-field side produced `pull_pct=1.0`, `oppo_pct=0.0`. Those labels should be reversed. The separate 45° and 50° boundaries also warrant validation against the coordinate system and a trusted directional leaderboard.

**Repair:** centralize handedness-aware direction classification; verify left- and right-handed examples and boundary cases; regenerate spray-dependent traits and charts.

### 3. High priority: “season” means different things across inputs

The BRef helpers used by [ingest.py:447](../baseball_construction/modules/ingest.py#L447) and the pitching equivalent request March 1–November 30. Their installed implementations explicitly include postseason dates. The saved 2022 Soto aggregate contains **716 PA and 165 games**, while MLB lists **664 regular-season PA**. [MLB player record](https://www.mlb.com/player/juan-soto-665742)

These totals are joined to Statcast-derived metrics intended to cover the regular season. This changes workload, rate denominators, percentile ranks, and deployment labels for postseason participants.

There is a separate raw-cache problem. `_regular_season()` filters new pulls, but the cache-hit branch in [ingest.py:235](../baseball_construction/modules/ingest.py#L235) returns existing contents without applying it. The saved 2024 file contains **20,583 spring-training pitches across 88 games**; 2016 contains another 252 spring pitches. Thus the filter's existence does not establish that the data is regular-season-only.

**Repair:** give every input the same explicit competition scope and cutoff. Validate and migrate existing caches as well as new downloads. Reconcile authoritative player totals before trusting merged metrics.

### 4. High priority: the date table omits regular-season games

[ingest.py:53](../baseball_construction/modules/ingest.py#L53) starts 2025 on March 27. The raw file has 2,428 games and 160 Dodgers games. The March 18–19 Tokyo games are regular-season games. [MLB Tokyo Series](https://www.mlb.com/international/events/tokyo-series)

The 2024 end date is September 29, excluding the September 30 Mets–Braves doubleheader. [MLB postponement notice](https://www.mlb.com/press-release/press-release-tonight-s-and-tomorrow-s-braves-mets-games-postponed)

Appending only after the maximum cached date cannot repair an omitted opening series, an internal missing day, or revisions to previously downloaded games. The nightly runner also stops when the calendar says the season is finished; its first run after the last game therefore needs an explicit finalization path to collect that last day's games.

**Repair:** reconcile against completed regular-season game IDs, use a short overlapping refresh window, and make finalization a validated state transition rather than just a date comparison. A maximum date alone is not a completeness check.

### 5. High priority: team profiles attribute full-season work to every team a player joined

[team_portrait.py:2915](../baseball_construction/modules/team_portrait.py#L2915) selects season-wide player rows by membership in a team's player-ID set. PA, BF, WAR, and role inputs are not split by stint. Both SD and WSH therefore receive Soto's same 716 PA and 5.47 WAR in 2022. Both LAD and WSH receive Scherzer's 761 BF and `workhorse` designation in 2021.

For scale, the 2025 NYY portrait sums to **7,560 hitter PA**, whereas its raw team batting events number **6,245**. LAD sums to 7,500 versus 6,115. The raw event counts are diagnostic counts, not reconciled official PA totals; nevertheless, the team membership join demonstrably duplicates full-season workloads. Postseason inclusion adds another distortion.

Full-season traits can reasonably describe a player. The problem is using full-season weights and deployment to describe his contribution to each particular team. The same duplicated player-season also becomes a potential perfect comp under another team key.

**Repair:** separate player-season identity from player-team-season contribution. Use stint PA/BF and team-specific deployment for roster weights; preserve season totals in distinct fields. Define whether the roster describes anyone who appeared, the final roster, or an as-of roster.

### 6. High priority: spin efficiency is dominated by clipping

[spin_efficiency.py:78](../baseball_construction/modules/spin_efficiency.py#L78) divides movement magnitude by `0.00153 × RPM / mph × 12`, then clips to [0,1]. On local raw inputs, **90.22% of non-null 2023 ratios and 90.15% of 2025 ratios are at least 1 before clipping**. The median unclipped ratio is about 3.0. The 2026 result is similar.

This destroys most per-pitch variation and leaves rankings strongly dependent on the residual unclipped pitches and pitch mix. A comment attributing a constant to Nathan does not establish the units or validate the estimator. Real active-spin inference also requires distinguishing Magnus and non-Magnus movement. [Nathan's active-spin analysis](https://baseball.physics.illinois.edu/ActiveSpin-v3.pdf)

**Repair:** suspend strong spin-efficiency claims until the estimator has an explicit physical derivation and comparison to an independent reference. Prefer a measured active-spin source where available. Do not merely change the constant until the histogram looks plausible. The existing spin test passes because it mainly checks shape and the already-clipped range.

### 7. High priority: refresh leaves important derived data stale

The refresh pipeline rebuilds tunnel data when raw Statcast changes, but `pitch_mix`, `spin_league`, `plate_discipline_league`, `mechanics_league`, and `sequencing_league` return existing parquet files without checking their inputs. See [pitch_mix.py:116](../baseball_construction/modules/pitch_mix.py#L116) and the loaders used in [team_portrait.py:3379](../baseball_construction/modules/team_portrait.py#L3379).

All five 2026 files were about **92.8 days older than raw Statcast**. The pitch-mix cache represents 191,141 pitches, compared with 713,868 typed pitches in the raw file. Some difference is intentional qualification filtering; the scale and cache behavior demonstrate that these are different snapshots. Forcing portraits does not force these loaders.

Also, `refresh --stages sources,...` updates CSV roots but does not reseed database player totals; the portrait preferentially reads those database totals. Nightly includes a seed step, but the general refresh command does not.

**Repair:** use one explicit dependency graph and source snapshot across raw data, canonical player tables, derived pools, and portraits. Invalidate every affected child or build into a new versioned directory. Test an incremental update against a clean rebuild.

### 8. Medium priority: reliability has missing gates and unvalidated statistical meaning

[reliability.py:125](../baseball_construction/modules/reliability.py#L125) maps the retired `wild` tag, but the live emitter produces `walk prone`. `fly-ball prone` is also absent while its opposite `ground-baller` is gated. An unmapped tag automatically passes.

A synthetic pitcher with **20 BF** receives both `walk prone` and `fly-ball prone`. Across saved portraits there are **751 walk-prone firings below 75 BF**, the configured half-stabilization sample for pitcher walks.

More broadly, PA/BF are reused for statistics whose actual opportunities are swings, balls in play, individual pitch types, or pitch pairs. The floor is **half** the configured stabilization value, contrary to the prose saying tags wait until that value. Calibration by “how many tags disappeared” measures product coverage, not estimation error or repeatability.

**Repair:** require each live tag to declare its evidence metric and sample unit; fail validation on accidental omissions. Evaluate split-season agreement and bootstrap tag stability by opportunity count. A hard gate can be a sound product decision without being described as proof that a player has a stable skill.

### 9. Medium priority: steal-attempt percentiles are team-relative

[team_portrait.py:946](../baseball_construction/modules/team_portrait.py#L946) ranks attempt rates within `team_bat`, not the league. Kevin Pillar's same season data ranks 66.7 on BOS and 33.3 on COL. Another saved multi-team season gives Amed Rosario 61.9 on CIN, 95.0 on LAD, and 56.25 on TB.

Consequently, identical player behavior can acquire a different trait just because teammates changed. Players with zero or one attempt are excluded from ranking, which also makes `low steal attempts` a statement about a selected subset of runners.

**Repair:** define and compute a season-wide eligible runner population once; disclose its qualification and the approximate opportunities denominator.

### 10. Medium priority: related pitch metrics use conflicting definitions

[pitch_mix.py:144](../baseball_construction/modules/pitch_mix.py#L144) counts foul tips as whiffs, and its `whiff_pct` denominator is all pitches. [pitch_aggregates.py:40](../baseball_construction/modules/pitch_aggregates.py#L40) counts foul tips as contact and computes whiffs per swing. The plate-discipline loader repeats the first convention. This creates incompatible values under similar names and affects out-pitch and velocity-adjusted-whiff claims.

Separately, [tunneling.py:193](../baseball_construction/modules/tunneling.py#L193) drops missing-location pitches before pairing, without checking that pitch numbers differ by one. A three-pitch test with an untracked middle pitch incorrectly paired pitches 1 and 3 as consecutive.

**Repair:** centralize pitch-outcome definitions, name both rates explicitly, and require true sequence adjacency. Keep the corrected closed-form tunnel geometry and ratio-of-means design, but validate pairing independently.

### 11. Medium priority: the service-time estimate has a wrong rule

[database.py:578](../baseball_construction/modules/database.py#L578) subtracts IL days from service time. MLB service accrues on the major-league injured list. [MLB service-time definition](https://www.mlb.com/glossary/transactions/service-time)

The calculation also assumes continued service between debut and the target season without reconstructing minor-league assignments or roster exits. Its 2020 branch grants a full year to anyone who debuted before that season ended, without establishing 2020 roster presence. These are structural problems in roster-control and pre-arbitration estimates, not small approximation errors.

**Repair:** use roster transaction intervals or an authoritative service ledger. Until then, label the result as a career-tenure proxy and avoid contractual categories. This affects built roster-control/philosophy data; I did not verify every remaining UI consumer of those legacy views.

## Confirmed engineering and consistency issues

### 12. High priority: failed builds can still publish and report success

[refresh.py:567](../baseball_construction/scripts/refresh.py#L567) discards the failure count returned by `stage_portraits`. Its publish stage only logs refusals. A mocked run with two failed portraits still invoked publishing and returned **0**.

[publish.py:438](../baseball_construction/scripts/publish.py#L438) continues with league and Scout publication after refusing a portrait. A mocked refusal reproduced both calls. Scout flattens the local portraits without the portrait freshness check. Nightly returns failure eventually, but also attempts publishing before acting on its accumulated build problems.

**Repair:** validate the complete candidate build before any publication; propagate failures immediately. Publish a versioned release and atomically switch an active-release pointer so readers cannot mix generations.

### 13. High priority: missing local files can become destructive Scout deletions

[publish.py:337](../baseball_construction/scripts/publish.py#L337) treats rows absent from the local portrait collection as stale and deletes them. The general CLI and refresh path publish Scout globally even when `--seasons` scopes the other artifacts. A partial checkout can therefore remove published seasons it never possessed. This behavior is documented in the CLI, but the lack of a complete-input preflight makes it unsafe operationally.

**Repair:** default every artifact to the same requested scope, require all 30 team inputs for each replacement season, and distinguish intentional deletion from missing/corrupt input. Test with a temporary fake database, not production.

### 14. High priority: the fingerprint does not prove data or code freshness

[team_portrait.py:2289](../baseball_construction/modules/team_portrait.py#L2289) hashes the FG roots and tunnel file, but not database player snapshots, the other league caches, several external sources, or function bodies. `_gate_digest()` excludes underscore-prefixed constants and does not cover imported helper implementations in archetype modules.

Replacing the outcome-tag function in memory left the fingerprint unchanged. A schema-21 portrait with **no fingerprint** was accepted. [rederive_traits.py:188](../baseball_construction/scripts/rederive_traits.py#L188) also stamps the current build fingerprint after replaying old gate inputs, without proving those inputs came from current data. This can relabel stale metrics as fresh.

**Repair:** distinguish data-snapshot identity, feature-definition version, trait-definition version, and presentation version. Hash exact dependencies or explicit build versions. Re-derivation should preserve its source identity and refuse replay when feature inputs need recomputation. Reject missing provenance after migration.

### 15. Medium priority: Compare keys lose the player's side

The database primary key includes `grp`, but `scout_rows` and `scout_comps` use only `player_id|team|season` in [schema_serving.sql:268](../baseball_construction/schema_serving.sql#L268). For a player represented as both a hitter and pitcher, the later row wins. Selecting a two-way hitter can therefore resolve the pitching profile and search pitcher comps.

**Repair:** carry side/group through option values and every lookup. Exclude duplicate team-stint copies of the same player-season from comp validation.

## Methodological limits, even after the bugs are fixed

- **Observed roster shape does not establish construction intent.** Appearance data can describe who played and how. Claims about why a front office built that roster require transactions, contracts, availability, and a defined decision date. Retrospective profiles are useful without implying causal intent.
- **Framing is an unadjusted proxy.** `compute_catcher_framing` subtracts one league called-strike rate across a broad shadow band. It does not estimate the expected call at each location or adjust for count, pitcher, batter, umpire, or pitch type. Stable pitcher/location differences can repeat across halves, so repeatability alone cannot assign the effect to catcher skill. The battery experiment does not resolve omitted pitch-location effects, and currently fails to import because `_FR_TOP` and `_FR_BOT` were removed.
- **Leverage is realized impact, not just opportunity.** The implementation uses mean absolute realized win-expectancy change. Standard leverage concerns the potential change before the outcome; a home run allowed can enlarge the implemented proxy. Call it an impact proxy or use pre-event leverage for deployment tags. [FanGraphs LI definition](https://library.fangraphs.com/misc/li/)
- **Expected-stat residuals are not pure luck.** `wOBA − xwOBA` includes context and model residuals. `Above/below expected` is supported more directly than a causal `lucky/unlucky` interpretation. ISO likewise measures extra-base production, not raw physical power alone; walk avoidance is closer to control than command-to-target.
- **Season and era comparisons answer different questions.** Hitter gates mostly use current-season ranks, while several pitcher outcomes and display metrics use a pooled era. Pool qualification differs between sources. Historical profiles deliberately include later completed seasons in their comparison population: acceptable for retrospective comparison, unsuitable for as-of backtesting unless frozen at the prediction date.
- **Similarity is a useful heuristic, not a validated scouting distance.** Thresholded sparse vectors discard differences below a gate and jump at gate boundaries. Correlated tags get repeated influence, categorical tags get full weight, and zero can mean typical, unmeasured, or unsupported. Cosine similarity can be 1 for two players sharing only one non-attribute tag. Self-neighbors are a sanity check, not sufficient validation.
- **The stored projection is retrospective.** `_compute_projected_profile` uses the realized roster and current-year workloads. It is a prior-performance counterfactual, not a preseason forecast. It also calls `build_hitter_traits` without PA, suppressing gated traits: the checked NYY/LAD 2025 projected trait densities contain only speed tags. The main UI has retired some legacy views, but these results still consume build work and remain in portraits.
- **Missingness needs its own state.** Broad exception handling often turns an unavailable feed into absent tags or a different comparison pool. Downstream displays can then interpret missing evidence as ordinary behavior. Store per-metric availability, sample count, source, cutoff, and fallback status; do not equate absence of a tag with evidence of absence.

## What is worth keeping

- The offline build / read-only serving architecture is appropriate for this scale. A separate service or distributed processing system is not justified by the current dataset alone.
- MLBAM IDs, the per-team-season artifact, evidence strings, stored gate inputs, and an explicit tag taxonomy are useful foundations.
- The serving schema uses RLS, explicit write revocation, and security-invoker functions; the dashboard explicitly chooses the anon credential. These are sound code-level choices, though deployed permissions were not audited.
- Bounded caches, per-key request coalescing, selected-column reads, and database-side filtering are practical optimizations.
- The corrected tunnel kinematics and ratio-of-means avoid specific earlier numerical problems. That does not validate the entire tunneling claim, but these choices are defensible.
- Treating player identity as multiple traits rather than forcing one archetype is sensible. Separate “not measured,” “insufficient evidence,” and “not distinctive” to make that idea work reliably.

## Where documentation differs from implementation

- **“Regular-season-only”**: cached spring games and BRef postseason totals remain, while the date bounds omit legitimate regular-season games.
- **“Every derived layer up to date”**: only tunnel has raw-data-driven refresh orchestration; five important league caches can remain stale, and general refresh does not synchronize seeded database totals.
- **“A run must verify it achieved its goal”**: checks exist, but the general refresh discards their return values and still returns success.
- **“Publish refuses stale portraits”**: applies to the portrait branch, not to every artifact derived from those portraits. League and Scout can still be published after refusal.
- **“Fingerprints cover current data and current logic”**: only a subset of input files and selected public constants are included; missing fingerprints are accepted.
- **“Archetype modules are no longer on the portrait path”**: the builder imports and calls `build_starter_profile` and `build_bullpen_profile`; hitter traits import helpers from `hitter_archetypes`. Some labels were retired, but the modules remain dependencies.
- **“Reliability refuses rather than shrinks”**: final tags use a gate, but spin and tunneling inputs still undergo shrinkage. The floor is 0.5 of configured stabilization, not the full point.
- **“A league-average player carries no tags”**: handedness attributes intentionally fire on essentially everyone. This statement only makes sense for selected non-attribute kinds.
- **“Generated references cannot drift”**: maps come from code, but incidence and evidence examples come from stored portraits; the check validates vocabulary coverage, not formulas, freshness, or denominators. It passed during this review.
- **Scale claims**: the READMEs say 2.3 million pitches per season; inspected full seasons have roughly 0.70–0.73 million. README player/tag totals differ from the local snapshot, and “player-seasons” counts duplicate team stints.
- **Operations example**: the “Verifying a rebuild landed” snippet calls `build_fingerprint()` without its required season argument. The “Everything” stage example omits publish.

## Engineering direction and repair order

1. **Create a canonical data contract.** Each metric needs a unit, numerator, denominator, direction, competition scope, observation cutoff, eligible population, and missing-value policy. Keep raw rates separate from ranks in field names and schemas. Normalize every upstream fallback into that contract before caching it.
2. **Fix the actual numbers.** Repair competition scope and game completeness, traded-player weights, contact and spray directions, and inconsistent pitch outcomes. Replace or suspend unsupported spin-efficiency claims. Repair sample-gate omissions and service-time semantics.
3. **Make builds reproducible and releases indivisible.** Build against immutable source snapshots; validate completeness and invariants; publish all related outputs under one release ID; activate only after success. Preserve the previous good release on failure.
4. **Add tests that could have caught these failures.** Official season-total reconciliation; no non-regular games; complete scheduled-game IDs; team-stint weights; metric direction; realistic spin references; fresh-vs-incremental equivalence; failure blocks all writes; missing files cannot delete unrelated seasons; and two-way identity resolution. Run these on pull requests. The current workflows build/seed/keep alive but do not run an independent correctness suite.
5. **Validate the claims statistically.** Use game- or time-blocked splits, report tag agreement and interval/threshold sensitivity, compare against independent reference metrics, and evaluate similarity over many players against simple baselines. Keep future seasons out of any predictive evaluation. Calibration should assess the intended claim, not merely tag incidence.
6. **Refactor the boundaries after behavior is protected.** Move analytics helpers out of dashboard/charts.py, put metric/tag definitions in an explicit registry, separate portrait orchestration from computation and serialization, and remove truly unused legacy outputs. The approximately 3,700-line portrait module and 5,000-line charts module make semantic changes difficult to audit.

Pin a tested dependency set and separate serving from build dependencies. For example, the code uses pandas `include_groups=False`, which the declared `pandas>=2.0` floor does not guarantee. Use migrations and schema checks instead of relying only on manual SQL execution. Keep per-stage timing, source coverage, cutoff dates, and failure reasons visible in build logs and release metadata.

The dominant scaling risk today is inconsistent duplicated state, not insufficient compute. Fixing contracts, provenance, and release integrity will improve both scientific trust and software maintainability more than adding infrastructure.
